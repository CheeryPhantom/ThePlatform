## 1. Privacy concerns + algorithm usability

### A. Privacy — what's wrong today

| Issue | Risk | Fix |
|---|---|---|
| DOB collected and required | Sensitive PII; invites age discrimination; we never actually use it | Drop the field. Keep `experience_years` (already separate). 1 hr |
| Gender collected with no purpose | Same as above for gender discrimination | Move to optional "self-ID" section, never expose to employers. 2 hr |
| Ward number required | Over-collection; city + province is enough for matching | Make ward optional (delivery-tier data only). 30 min |
| Phone numbers unverified | Anyone can put anything in; spam/scam risk | OTP verification via Sparrow SMS or Twilio. M effort, ~NPR 1/SMS |
| JWT in `localStorage` | XSS = full account takeover | Move to HttpOnly cookie + CSRF token. L effort, ~3 days |
| No privacy policy | Legal exposure; trust signal | Write one. Use [Termly](https://termly.io) or [iubenda](https://www.iubenda.com) templates as starter. 1 day |
| No T&Cs | Same | Same |
| No data export | GDPR / good-faith data hygiene; users can't take their stuff | `GET /api/users/me/export` returns a zip (profile JSON + uploaded files). M effort |
| No account deletion | Required by GDPR-equivalent; current "soft delete" doesn't include their applications, files, badges | `DELETE /api/users/me` cascading + grace period. M effort |
| No "why we ask" copy on sensitive fields | Trust | Add tooltip on DOB, gender, salary, phone fields. S effort |

**Decision needed**: do we drop DOB + gender entirely, or keep them optional? My vote: drop DOB (compute experience from `experience_years`), make gender optional self-ID never shown to employers.

**Decision needed**: privacy policy + T&Cs — who writes the first draft? I can scaffold from a template; someone needs to read carefully before publishing.

### B. Algorithm — what's wrong today

The match score is a simple Jaccard ratio (matched skills / required skills × 100). It's transparent (good for fairness) but has three real bugs:

**Bug 1: No skill normalisation.** `React`, `ReactJS`, `React.js`, `react` are all stored separately. A candidate listing `React` doesn't match a job requiring `ReactJS`. This is the single biggest fix.

**Implementation**:
```sql
CREATE TABLE skill_aliases (
  canonical TEXT NOT NULL,           -- e.g. "react"
  alias TEXT NOT NULL,               -- e.g. "reactjs", "react.js"
  PRIMARY KEY (alias)
);
```
Seed file ~150 rows for the IT/Finance taxonomy we already have. Then in the match function:
```js
const normalize = (skill) => {
  const lower = skill.toLowerCase().trim();
  return aliasMap.get(lower) || lower;
};
```
Apply before comparing. **Effort: half a day** including seeding.

**Bug 2: "0% match" is misleading.** A candidate strong in 8 skills the job didn't list reads "0%" if they don't have the 1 required skill. Fix:
- Below 40%: don't show a percentage bar, show a "Stretch" tag
- 40–74%: show partial
- 75–89%: good fit
- 90+: strong fit

Also surface absolute count: "**You have 3 of 5 required skills**" on every card. Numbers feel less judgmental than percentages.

**Bug 3: No experience-years weighting.** A 0-year candidate and a 10-year candidate get the same score if they both list React. Add a soft penalty when `experience_years < requirements.years_of_experience_min`.

**Effort total for algorithm fixes**: 1–1.5 days. Highest single ROI.

## 2. POE / shared AI tooling

### A. What POE actually is

POE.com (Quora's product) gives one subscription that fans out to Claude, GPT-5, Gemini, Llama, image models, custom bots. **~$20/month for a shared seat.**

### B. When POE wins vs direct APIs

| Use case | Tool | Why |
|---|---|---|
| Drafting copy / UX writing | POE | Compare Claude vs GPT in seconds |
| Brainstorming features | POE | Multiple angles cheap |
| "Is there a smarter way to do this?" | POE | Get a second AI opinion fast |
| Image gen for slides/mocks | POE | Multiple image models in one place |
| Code in production | Direct API (Claude/OpenAI) | No reproducibility on POE |
| Structured data extraction | Direct API | Too clicky on POE |
| Anything with >100k tokens | Direct API | Free tier limits |

### C. Concrete setup

1. **One paid POE seat** — credentials in shared 1Password vault. ~NPR 2,800/month.
2. **Shared notes doc** — `/docs/ai-notes.md` in the repo, or a Notion page. Format:
   ```
   ## 2026-06-01 — Drafting marketing landing copy
   Tried: Claude 4.7, GPT-5, Gemini 2.5
   Winner: Claude — kept the Nepali context, GPT was too US-corporate.
   Prompt that worked: "...write copy for Nepali IT job seekers..."
   ```
3. **Weekly "AI finds" channel post** — anyone shares what worked. Prevents knowledge silos.
4. **No-go**: don't let POE outputs ship straight to production without review. Always have a human edit pass.

### D. Alternative worth considering

**OpenRouter** ($) — same fan-out concept but API-first, pay-per-request, no monthly subscription. Better when you want to programmatically test multiple models on the same input. ~$5–15/month at our usage.

**Recommendation**: start with POE for exploration; if we end up wanting programmatic comparison, layer OpenRouter on top.

## 3. NAS — inhouse + (don't do) Storage-aaS

### A. Decision: build inhouse, kill the SaaS idea

**Inhouse NAS — yes.** Reasoning in the previous review still stands: ~1-year payback vs cloud subscriptions, removes friction, privacy-friendly.

**Storage-aaS — no.** The market has Backblaze, Wasabi, iDrive at $5/mo/TB with global redundancy and enterprise SLAs. Our cost-of-goods-sold (drives + power + a residential connection) doesn't beat them, our reliability story doesn't match them, and we'd burn months on billing/support instead of building The Platform. Skip permanently.

### B. Hardware recommendation

**Option A — Synology DS923+** (recommended)
- DS923+ unit: ~NPR 90,000 (~$650)
- 4× Seagate IronWolf 4TB drives: ~NPR 100,000 (~$720 total)
- 16GB RAM upgrade (optional): NPR 12,000
- UPS (APC BR1000G or local equiv): NPR 15,000
- **Total: ~NPR 215,000 (~$1,500)**

You get: SHR-2 redundancy (2 drives can die), Time Machine for Macs, hosted Git/Postgres via Container Manager, easy VPN setup, Snapshot Replication, official mobile app.

**Option B — UnRAID on old PC** (cheap option)
- Old i5/i7 desktop you have lying around: free
- 4× HDDs: ~NPR 100,000
- UnRAID license: $59 lifetime
- **Total: ~NPR 110,000**

You get: more flexibility, less polish, more setup time. Good if someone on the team enjoys this.

### C. What it'll host

1. **Shared assets** — designs, screen recordings, mockup PSDs (replace Dropbox/Drive)
2. **Time Machine + Veeam backups** — every machine in the team backed up nightly
3. **Self-hosted Postgres for staging** — separate from Supabase prod
4. **Self-hosted Gitea (optional)** — private repos without GitHub paid tier
5. **Plausible analytics** — privacy-friendly, self-hosted alternative to GA
6. **Family/personal use** — whoever houses the NAS gets bonus value

### D. Access + security

- **Tailscale free tier** for remote access — 100 devices free, zero-config WireGuard. No need to expose the NAS to the public internet.
- **SHR-2 RAID** — survives 2-drive failure
- **Nightly off-site backup to Backblaze B2** — ~$5/mo per TB. Insurance against fire/theft/ransomware.
- **Encrypted shared folders** for sensitive stuff (encryption-at-rest)
- **2FA on the Synology admin account**
- **No port forwarding ever** — Tailscale only

### E. Operational questions to decide today

1. **Where does it physically live?** Someone's apartment with stable power + UPS + ideally fibre.
2. **Who is the maintainer?** One person owns updates, drive replacements, backup health. Rotating role doesn't work for infra.
3. **What's the budget cap?** NPR 215k for Synology vs 110k for UnRAID. I'd take the Synology — the time saved on setup pays for itself.
4. **Off-site backup target?** Backblaze B2 or another founder's NAS (mutual backup).

## 4. No-code visual editor for our admin layer

### A. Decision: don't build it; use Plasmic for visual + design tokens for the rest

Building a no-code visual editor is years of engineering. Tools to leverage instead:

### B. The three problems people want a visual editor for

**Problem 1: "Designers want to tweak landing pages without bothering devs."**

→ Solution: **[Plasmic](https://www.plasmic.app)**. Visual editor for React components. Designer edits in Plasmic Studio; the React app pulls components at runtime or build time.
- Free tier: 3 projects + 500k monthly page views — enough for landing + a few marketing pages
- Paid: $39/mo for more projects
- 2-day setup to wire one page (the landing page)

**Problem 2: "Marketing/content people want to edit copy without devs."**

→ Solution: headless CMS. Options:
- **Sanity** — free for small teams, real-time studio, great DX. Best for content-heavy stuff (blog, FAQ, terms).
- **Strapi** — self-hostable (could live on the NAS), more flexible, more setup.

**Problem 3: "We want to change colours/spacing/type without code."**

→ Solution: **design tokens in CSS variables** (we already have them in `index.css`). One person owns the file; anyone can suggest changes via PR. No tool needed.

### C. Concrete recommendation

1. **Phase A (now)** — tighten the design tokens file. Document what each variable means. Anyone can propose changes.
2. **Phase B (when we have a real landing iteration to do)** — try Plasmic on the landing page. 2-week experiment, free tier. If it sticks, plasmify the static pages (footer, about, faq).
3. **Skip the headless CMS entirely** until we have evergreen content worth managing.

**Don't build anything custom.** Every hour spent on a custom CMS is an hour not spent on the actual product.

## 5. Algorithm accuracy testing — actual implementation

### A. Phase 1 — ground-truth harness (2–3 days)

**What we're building**: an admin-only page that shows a candidate-job pair and asks the rater to score the fit. We collect ~500 ratings, then compute correlation with the algorithm.

**Schema**:
```sql
CREATE TABLE match_ratings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  rater_user_id UUID REFERENCES users(id),
  job_id UUID REFERENCES jobs(id),
  candidate_user_id UUID REFERENCES users(id),
  rating TEXT NOT NULL CHECK (rating IN ('great', 'decent', 'poor', 'no_fit')),
  rationale TEXT,
  algorithm_score INT,  -- what the algorithm said at the time of rating
  algorithm_version TEXT,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now(),
  UNIQUE (rater_user_id, job_id, candidate_user_id)
);

CREATE INDEX idx_match_ratings_pair ON match_ratings(job_id, candidate_user_id);
```

**UI** (`/admin/rate` page, employer-only or admin-only):
- Picks an un-rated pair at random (or from a curated set)
- Shows the job (title, description, required skills) side by side with the candidate (headline, skills, experience, resume link)
- Four big buttons: Great fit / Decent / Poor / No fit
- Free-text "why?" box (optional)
- Auto-saves and advances

**Analysis script** (one-off Node script):
- Load all ratings
- Compute Spearman correlation between rating-as-ordinal and algorithm score
- Print top 20 disagreements (algorithm 90+ but human rated `no_fit`, or vice versa)
- These disagreements are gold — they tell you what the algorithm misses

**Stop condition**: 500 ratings is enough for a first read. Should take a team of 3 about a week of evenings.

### B. Phase 2 — behavioural signals (always-on)

Once you have actual applications flowing, the algorithm's calibration is measurable:

- **Apply rate by match band**: of all candidates who *saw* a job at 90+ match, what % applied? Compare to the 50–74 band. The high band should apply at meaningfully higher rate.
- **Shortlist rate by match band**: of all applicants, what % got moved to `shortlisted`? Should correlate with match score.
- **Time to shortlist by band**: high-match applicants should get acted on faster.

**Schema additions** (only if not already there):
```sql
-- Page view events (might want to add)
CREATE TABLE job_views (
  id BIGSERIAL PRIMARY KEY,
  job_id UUID REFERENCES jobs(id) ON DELETE CASCADE,
  user_id UUID REFERENCES users(id) ON DELETE SET NULL,
  match_score INT,
  match_algorithm_version TEXT,
  viewed_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
```

**Dashboard view** (admin/analytics):
- Bar chart: apply rate by match band
- Bar chart: shortlist rate by match band
- Updated nightly

### C. Phase 3 — synonyms + measurement loop

The single highest-impact lever. Process:

1. Build `skill_aliases` (see section 1.B above)
2. **Before deploying**: snapshot the match-score distribution across all live candidate-job pairs
3. **Deploy**, recompute the same distribution
4. Expected: median score jumps 15–25 points, "0% matches" drop dramatically
5. If yes, ship. If no, debug.

### D. Phase 4 — A/B framework

Once we have signal from Phase 2, we can test changes safely:

```js
// Pseudo: route 10% of users to v2
const algorithmVersion = (req.user.id.charCodeAt(0) % 10 === 0) ? 'v2' : 'v1';
```

Tag every `job_views` row with the version. Compare apply rate v1 vs v2 after a week.

## 6. Meeting cadence — concrete proposal

### A. The proposal

| Cadence | Format | Length | Purpose |
|---|---|---|---|
| Daily | Async Slack/Discord post | 1 minute | Status, blockers |
| Weekly | Sync call (Mon 9am) | 30 min | Align priorities, unblock |
| Bi-weekly | Brainstorm / retro (Fri 4pm) | 60 min | Review, plan, weird ideas |
| Monthly | Written review (anyone) | 5 min to read | Big picture |
| Monthly | Social (dinner / coffee) | Whatever | Cohesion |

### B. Templates

**Daily async post**:
```
**Yesterday**: <what shipped>
**Today**: <what's planned>
**Blocked**: <or "no blockers">
```

**Weekly sync agenda** (written before the meeting in a shared doc):
- 5 min — anything urgent that broke
- 10 min — what each person is shipping this week
- 10 min — blockers, decisions needed
- 5 min — anything else

If the agenda is empty by Monday morning, cancel the meeting.

**Bi-weekly brainstorm**:
- 15 min — what shipped last 2 weeks, what metrics moved
- 20 min — what's the next bet
- 25 min — pure ideation, no decisions, just write things down

**Monthly written review** — one doc, one writer (rotates), takes 30 min to write:
- What shipped
- What's the biggest risk right now
- What's the next bet
- 1 chart from the analytics dashboard

### C. Tooling

- **Async + chat**: Slack or Discord. Discord is free, Slack has better integrations. Either is fine.
- **Agenda docs**: Notion (paid), Obsidian (free + git sync), or markdown in the repo's `/docs` folder. I'd use the repo for permanence.
- **Decision log**: `/docs/decisions/` — ADR-style markdown. One file per decision. Future you will thank present you.
- **Calendar**: Google Calendar, recurring invites. Treat them as sacred — moving the weekly sync should require team consent.

### D. What kills small-team velocity

- Daily standups (we're not a 30-person team)
- Meetings without agendas
- Decisions made in meetings instead of in writing
- "Quick syncs" that become 90-minute therapy sessions
